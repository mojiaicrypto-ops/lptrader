# D3 — 架构决策（2026-09-30 确认）

**性质**：本文记录**仍然生效**的架构决策。原文件 `docs/product/iteration-2-architecture.md` 因含大量版本对比（"重构前/后"）已被归档，其决策内容与不变量迁移至此与产品文档。

---

## D3.1 模块划分：四模块与分层

**决定**：系统分为四个模块，筛选层与执行层分离。

```text
模块 1 · 池子发现     纯 HTTP，每 60 分钟，可失败、可缓存
模块 2 · 逐池精筛     链上，建仓前按需，首个合格即停
模块 3 · 持仓监控/风控 链上，5min + 15min
模块 4 · 换池         事件驱动
```

**依据**：模块 1/2 是筛选层（便宜、可失败），模块 3/4 是执行层（贵、必须成功、涉及资金）。**混合两者会导致：每轮扫描对全部候选做链上探测**（实测 20 组合 × fee tiers）、**监控对全部 11 个 token 做 `uiMultiplier` 探测**（33 次调用且缓存 TTL = 间隔，必然错过）。

**模块 1 不读链**是硬约束：链上验证统一归模块 2。

## D3.2 候选排序：`apr7d` 主序 + `tvlUsd` 次序

**决定**：当前用两级排序；时序数据足够后升级为基线 §21 的完整综合池分。

**依据**：§21–§26 的池分含 `VolumeStability`(15%) 与 `AssetStability`(15%)，**两者都需要历史序列**，而时序表新建、尚无足够历史。§22 禁止单独使用 1D APR —— 用 7d 已满足。

**升级触发条件（写死，避免变成"永远不做"）**：

```text
pool_snapshots 覆盖 >= 4 周 且 每池有效样本 >= 200
→ 实现 §21 五分量加权池分，替换两级排序
```

**升级前**：决策日志必须记录"当前排序为 apr7d+tvlUsd，非综合池分"，使判据可审计（§77）。

## D3.3 模块 3 只读持仓 token + 低频全量兜底

**决定**：每轮只读持仓的 2 个 token + native；另有每 60 分钟一次的全白名单扫描作为兜底。

**依据**：NAV 正确性只依赖**实际持有的资产**；未持有时其 `uiMultiplier` 算错不影响任何数字。

**遗留风险**：若手动往钱包转入白名单内的其他 bStock，最多 60 分钟内不被计入 NAV。
**方向上安全**：漏算使 NAV **偏低** → §66 回撤线**更早触发** → 保守方向的误报，不是危险的漏报。

---

## D3.4 池子时序落库

**决定**：每次采样写一行到 SQLite，形成时间序列。

**依据**：§59「TVL 24h 骤减」需要**两个时间点**。无时序则该风控**永远算不出** —— 这是"风控判据缺数据源"，不是"少存一点数据"。

**保留期**：可配置；`pruneBefore` 定期清理。

## D3.5 换池（原"模块 4"）的触发分类

> **术语纠偏**：曾用"模块 4 · 换池"统称，掩盖了重要区分 —— **"能不能撤池"与"会不会自动换池"是两件事**。

**三种撤池触发，性质完全不同**：

| 类型 | 触发者 | 依据 | 状态 |
|---|---|---|---|
| **A. 风控自动撤池** | 程序 | §55 脱锚 / §58 紧急 / §59 TVL 崩 / §66 NAV 触及风控线 | ✅ 已接线 |
| **B. 人工撤池** | 用户 `/exit` | 用户决定 | ✅ 撤池可用；**撤后重建未接线** |
| **C. 风控驱动的换池**（撤→找新池→建仓→回监控） | 程序 | §32（风控事件豁免冷却） | ❌ 未接线 |

**即时状态以 [feature-list.md](../product/feature-list.md) 为准。**

**曾经的理由，现已失效**：原先以"模块 3 未接线"为由推迟换池。该前提**已不成立**（模块 3 已接线并可运行），因此**换池不再是"推迟项"，而是闭环的必要部分** —— 见 [development-plan.md](../plan/development-plan.md) P1。

## D3.6 人工命令的确认策略

### `/exit` —— 撤池

| 项 | 决定 | 理由 |
|---|---|---|
| 确认门 | **需要**（推送 Approve/Reject） | 撤池不可逆：有 swap 成本 + 实现 IL |
| 执行内容 | Collect Fees → Remove Liquidity（100%）→ **两腿全部换成 U** | §5.3.1 要求撤完回到纯 U，否则下次建仓起点不是纯 U |
| 撤完去向 | **停在 `IDLE`，等手动 `/start`** | **2026-10-02 用户决策**（见 D3.8，推翻"自动重新选池"） |
| 重建仓是否再确认 | **不自动重建**，由 `/start` 走它自己的授权路径 | 换池是"新的一轮决策"，不是本次撤池的延续 |
| 换池门槛（§28–§32） | **不适用** | 那些门槛防止**程序**频繁折腾，不约束用户 |

**仍保留成本上限**。

**"确认一次"的范围**：`/exit` 的那一次确认，覆盖 **Collect → Remove → 换 U** 整条链。链内的 swap 与 addLiquidity 不再逐笔请求人工确认 —— 逐笔确认会把一次授权拆成四次点击，用户会开始无条件点 Approve，闸门反而失效。**确认的对象是"这笔决策"，不是"这笔交易"。**

链内的安全不靠重复确认，靠：§40/§41 报价闸门、§95 写路径 guard、滑点上限、以及每一步先等到上一笔落块（`Remove` 未确认就 `swap`，读到的是过期的余额）。

### `/start` —— 手动建仓

| 项 | 决定 | 理由 |
|---|---|---|
| 确认门 | **不需要** | 命令本身即授权 |
| 前提 | 必须 `IDLE` | 已持仓时应拒绝并提示 `/exit` |
| 行为 | 走**同一**选池与建仓逻辑 | 不另写一套 |

### `/resume` —— 风控停机后放行

显式人工动作。恢复**不自动重建仓** —— 回到 `IDLE`，建仓需另发 `/start`。两个决定分两步：「我接受现状」与「重新投钱」。

## D3.7 弃用 §42 原子建仓（2026-10-02）

**决定**：`runAtomicBuild` 移除，`runTwoStepBuild` 成为唯一建仓路径；`AddLiquidityRequest.swapForDeficit` 随之废弃。两个 DEX（PancakeSwap V3、Uniswap V3）统一走：

```text
swap → 等落块 → 读钱包实际余额 → addLiquidity（实际值）→ 等落块
```

**理由**：

1. 原子路径（`Position.fromAmounts` + `swapAndAddCallParameters`）要求在发送前就算准 swap 的产出 —— `fromAmounts` 的参数是"swap 之后应有的余额"。
2. §5.3.3（按实际余额建池）是资金安全规则；原子性只是 gas 优化。二者不可兼得，规则赢。
3. 实证（2026-10-01，AAPLB/USDT，真金）：原子路径三次全部 `execution reverted: Price slippage check`；两步路径第一遍即通过。

**代价与补偿**：多一次 gas；swap 与 mint 之间多一个窗口。窗口风险由 §5.3.5 等待落块覆盖，不由原子性消除。

**清理义务**（T5 落地时）：移除 `supportsAtomicBuild` 对执行路径的分叉作用（标志保留，仅描述 DEX 能力）、`runAtomicBuild`、`swapForDeficit`，及所有引用 §42 原子语义的测试与文档段落 —— 不留兼容垫片。

## D3.8 撤池后不自动重建（2026-10-02，推翻 D3.6 的"自动重新选池"）

**决定**：无论手动 `/exit` 还是风控灾难级自动撤池，撤完（含两腿换 U）一律停在 `IDLE`，**重建仓只能由操作者显式 `/start` 触发**。

**理由（用户原话为准）**："撤池后，我再运行 `/start`，不是又开始新一轮了吗" —— 手动路径本来就是一个完整闭环。
- 手动 `/exit`：撤池换 U → IDLE。操作者自选时机开新一轮。
- 风控自动撤池（灾难级）：同样停 IDLE。无人值守时段**宁可资金闲置到操作者醒来**，也不让机器人在重大风险事件（往往伴随剧烈波动）中自行再进场。
- **随之失效**：§32"风险事件豁免冷却与收益门槛"、§6.4 自动重建成本上限（`rebuildPolicy` 模块删除）、计划 T10/T11/T12。
- 代价（已接受）：灾难发生在深夜时资金闲置至人工介入。换来的是：自动线只剩"撤池保命"一个动作，策略行为对操作者完全可预测。
